# 길드 레이드 던전 (migration 158, 신규 콘텐츠, 사용자 요청 "던전 컨텐츠 위주로 여러개")

관련 파일: `GuildRaidBattle.jsx`, `lib/guildRaid.js`, `DungeonSelect.jsx`(`GuildRaidPanel`), migration 158

## 개요

길드(154)는 소속감/랭킹까지는 있었지만 "길드원들이 함께 협력해서 처치하는 목표물"이 없었음 — 방치형 RPG 업계에서 길드 시스템의 완성도를 크게 좌우하는 요소가 바로 **비동기 협동 레이드**. 월드보스([`world-boss.md`](./world-boss.md))를 그대로 축소 복제해서 "전체 서버 공용 체력" 대신 **"내 길드(최대 30명) 전용 공유 체력"**으로 스코프만 좁힘.

- 매주 일요일 자정(서울시간) 리셋, 길드마다 독립적인 보스 인스턴스(`guild_raid_state` PK가 `(guild_id, week_key)`)
- HP 1,500만 / ATK 3,500 / DEF 1,000 — 월드보스(HP 3,000만)의 절반 규모로, 서버 전체 인원이 아니라 길드원(최대 30명)만 참여한다는 점을 반영
- 하루 3회 도전, 한 판당 제한시간 1분(월드보스와 동일 UX)
- 클리어 시 기여 피해량에 비례한 골드를 **즉시 우편함으로** 지급, 주가 끝날 때까지 못 잡아도 그동안 입힌 피해량만큼 **소정의 위로 보상**을 우편으로 지급(월드보스와 동일한 "실패해도 완전히 헛수고는 아님" 설계)

## 보안 설계 — 월드보스의 교훈을 처음부터 반영

월드보스는 033(최초 출시) 당시 세션 검증이 없어서, 036에서야 뒤늦게 "`report_world_boss_damage`를 입장 절차 없이 무한 반복 호출하면 하루 3회 제한이 완전히 무력화된다"는 취약점을 발견해 패치했음([`world-boss.md`](./world-boss.md), [`security.md`](./security.md) 참고). 길드 레이드는 **처음부터** 같은 패턴을 적용:

- `guild_raid_sessions` 테이블 신설 — `enter_guild_raid()`가 세션을 실제로 발급/기록
- `report_guild_raid_damage(p_session_id, p_damage)`는 그 세션이 "존재 + 본인 것 + 아직 안 썼음"일 때만 데미지를 반영하고 즉시 `claimed = true` 처리 — 세션 하나당 데미지 보고는 정확히 1회만 가능
- 데미지 자체도 월드보스와 동일하게 `least(p_damage, my_combat_power*60, boss.current_hp)`로 전투력 기반 상한 클램프

## 배포 전 시뮬레이션 검증에서 발견/수정한 버그

`enter_guild_raid()`의 반환 컬럼명(`guild_id`, `week_key`)이 `guild_raid_state` 테이블의 실제 컬럼명과 완전히 동일해서, 함수 본문에서 `where guild_id = v_guild_id`처럼 **테이블 별칭 없이** 조회하면 PL/pgSQL이 "이게 OUT 파라미터냐 테이블 컬럼이냐" 구분을 못 해 컬럼 모호성 오류가 날 수 있는 코드가 초안에 있었음(과거 감사 68/69에서 문서화된 것과 동일한 클래스의 실수, [`attendance-and-achievements.md`](./attendance-and-achievements.md) 참고). 배포 전 전체 함수를 대상으로 "OUT 파라미터명과 겹치는 bare 컬럼 참조"를 정적 스캔해서 발견 → `guild_raid_state grs where grs.guild_id = ...`로 테이블 별칭을 붙여 수정. 나머지 함수들은 스캔 결과 전부 안전(정상적인 별칭 사용 또는 INSERT 타깃 리스트라 애초에 모호성이 발생하지 않는 문맥)함을 확인.

## 클라이언트 설계

- `GuildRaidBattle.jsx`는 `WorldBossBattle.jsx`를 복제해서 만듦(공용 체력 보스와 싸우는 전투 로직 자체가 거의 동일 — 데미지를 서버에 보고하고 결과를 받는 구조). 개인 최고기록(personal best) 공유 기능은 길드 레이드에서는 빼서 단순화(길드 단위 협동이 핵심이라 개인 기록 경쟁 요소는 다음에 필요해지면 추가)
- 데미지/공격 텀 수치는 월드보스보다 약간 낮춤(정상 6,000 / 스킬 13,000 / 0.8초 텀) — 참여 인원이 훨씬 적은 소규모 길드(최소 인원)도 현실적으로 버틸 수 있게
- `DungeonSelect.jsx`의 `GuildRaidPanel`은 길드 미가입 유저에게 "길드 찾으러 가기" 버튼을 보여주고 누르면 친구/길드 탭(`onGoToGuild`)으로 이동 — 길드 가입 자체는 기존 `GuildPanel.jsx`([`guild.md`](./guild.md))가 담당, 이 문서의 범위는 레이드 전투만
- `guildRaid` state는 `undefined`(로딩중) / `null`(길드 미가입, 정상) / 객체(정상) 세 가지를 구분해서 로딩중과 미가입을 헷갈리지 않게 함

## [긴급/치명적] 버그 수정 이력 (migration 161)

배포 직후 78차 정기 보안점검에서 `sync_guild_raid`(미클리어 주간보상 정산)가 다른 기여자에게 `add_gold`를 직접 호출하고 있던 걸 발견 — `add_gold`는 `auth.uid() = target_user`일 때만 동작하는데, 이 루프는 "새로 입장한 사람" 기준으로 실행되면서 **다른 유저**에게 지급을 시도해서, 지난주 기여자가 2명 이상이면(길드 레이드는 항상 그런 상황) 트랜잭션이 롤백되고 그 길드는 새 레이드를 영구히 시작할 수 없는 상태에 빠질 수 있었음. 정확히 월드보스가 [`world-boss.md`](./world-boss.md)의 110에서 겪었던 것과 동일한 버그(158 작성 시 월드보스의 옛 버전을 참고했던 게 원인). add_gold 직접호출을 제거하고 우편(claim_mail) 단일경로로 수정 — 자세한 경위는 [`security.md`](./security.md) 78차 참고. `report_guild_raid_damage`(클리어 시 즉시보상)는 애초에 우편 단일경로로 올바르게 작성돼있어 영향 없었음.

## 알려진 제한

- 클리어 보상에 월드보스의 "용의 버프"(공격력·방어력 2배) 같은 별도 버프는 없음 — `profiles.dragon_buff_until` 컬럼을 재사용하면 두 시스템의 버프 의미가 섞여 헷갈릴 수 있어 이번엔 골드 보상만으로 범위를 좁힘. 반응이 좋으면 길드 전용 버프 컬럼을 새로 만들어 추가하는 걸 검토
- 길드원 전체 실시간 진행 상황(누가 지금 도전 중인지)은 안 보임 — 기여도 랭킹만 조회 가능(비동기 협동)
