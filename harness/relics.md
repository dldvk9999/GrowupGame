# 유물(Relic) 시스템 (migration 119/120, 신규 콘텐츠, 사용자 요청)

관련 파일: `RelicGacha.jsx`, `lib/relicCatalog.js`, `lib/relicGacha.js`, `lib/relicBonus.js`, migration 119/120

## 개요

스킬 뽑기와 동일한 단일 풀 구조(전역 뽑기레벨, `profiles.total_relic_draws`)로 50종 유물을 뽑는 콘텐츠. 장비와 다른 점은:
- **중복 = 강화 시도**(장비는 100% 자동 강화, 유물은 실패할 수 있음)
- **최대 5개까지만 장착**해야 전액 효과가 적용됨(131에서 3→5로 확장, 사용자 요청)
- ⚠️ **보유효과 신설(migration 141, 신규, 사용자 요청)**: 처음엔 "장비/스킬은 보유만 해도 소량의 보유효과가 있는데 유물은 그게 없음(장착개수 제한이 유일한 안전장치)"이 설계 원칙이었는데, 이번 요청으로 유물도 **장착 여부와 무관하게 보유한 것 전부**가 장착효과의 일부만큼 기여하도록 바뀜(`RELIC_POSSESSION_RATIO`, 최초 10% → 145에서 20%로 재상향) — 장착개수 제한(5개)은 여전히 메인 안전장치로 유지
- ⚠️ **`relic_catalog` RLS 미적용 수정(migration 180, Supabase 린터 지적 — 사용자 제보)**: 119 작성 당시 "정적 카탈로그라 RLS 없이 전체 공개(다른 catalog 테이블들과 동일 패턴)"라고 판단했었는데, 실제로는 이 게임의 다른 카탈로그 테이블(`item_catalog` 등)이 전부 RLS를 켜고 "누구나 조회 가능" 정책을 명시하는 방식이었음 — `relic_catalog`만 유일하게 RLS 자체가 꺼진 예외였음(56개 테이블 전수 스캔으로 확인). 데이터 자체는 원래도 민감하지 않은 정적 밸런스 수치라 실질적 유출 위험은 없었지만, 다른 카탈로그 테이블들과 동일한 방어 계층(RLS on + 전체공개 정책)으로 맞춤
- ⚠️ **버그 수정(사용자 제보 — "유물 뽑기 후 뽑기레벨/경험치가 화면에 바로 반영 안 됨")**: 뽑기레벨은 `profile.total_relic_draws`에서 파생되는데, `RelicGacha.jsx`의 뽑기 성공 처리에 이 값을 갱신하는 경로가 아예 없었음(스킬 뽑기는 `refreshSkills`가 뽑을 때마다 `profile`을 통째로 다시 받아와서 이미 정상 동작했고 — [`skills.md`](./skills.md) 참고 — 유물만 이 처리가 빠져있었음). `onDrawCountChange` 콜백을 `RelicGacha` → `Shop.jsx` → `App.jsx`로 새로 연결해서 뽑은 즉시(`results.length`만큼) `profile.total_relic_draws`를 클라이언트에서 낙관적으로 증가시키도록 수정. 같은 김에 스킬 뽑기에도 동일한 낙관적 업데이트를 추가해서(반응속도 개선, 버그는 아니었음) 네트워크 왕복 없이 더 즉각적으로 보이게 함

## 유물 카탈로그 (50종)

효과 카테고리 7종 × 수치(flat)/비율(percent) 방식을 섞어 10개 원형(archetype)을 만들고, 5개 등급에 각각 10개씩 배치:

| 카테고리 | flat | percent |
|---|---|---|
| 체력(hp) | ✅ | ✅ |
| 공격력(atk) | ✅ | ✅ |
| 방어력(def) | ✅ | ✅ |
| 스킬 쿨타임(cooldown) | — | ✅ |
| 골드 획득(gold) | — | ✅ |
| 경험치 획득(exp) | — | ✅ |
| 버프 효과(buff) | — | ✅ |

체력/공격력/방어력은 "고정 수치로 늘어나는 것"과 "비율로 늘어나는 것" 둘 다 존재(사용자 요청 반영)하도록 flat+percent 둘 다 만듦. 쿨타임/골드/경험치/버프는 원래 성격상 비율(%) 단위가 자연스러워서(예: "쿨타임 -0.6%") percent만 만듦 — flat 버전(예: "쿨타임 -30ms")은 스킬마다 쿨타임 격차가 800ms~22000ms로 워낙 커서 의미가 옅어질 것 같아 제외.

등급 배율은 장비 등급 배율(`itemCatalog.js RARITIES`)과 동일하게 1 / 1.8 / 2.8 / 4.2 / 6.5 — 다른 시스템과 감각적으로 통일.

## 강화 (최대 +200, 실패 확률 있음)

중복 유물을 뽑으면 **강화 시도**가 발생함:
```
성공확률 = max(0.30, 1 - 현재레벨 × 0.0035)
```
- 레벨 0→1(첫 중복): 100%
- ⚠️ **만강(200) 중복 시 루비 보너스(migration 150, 신규, 사용자 요청)**: 이미 200강까지 강화된 유물이 또 중복으로 나오면, 기존엔 그냥 아무 보상 없이 버려졌음(완전 헛뽑기) — 이제 **15% 확률로 루비 1~10개**(랜덤)를 대신 받음. `draw_relic`/`draw_relic_batch` 둘 다 반환 컬럼이 `bonus_rubies` 하나 늘어서 DROP FUNCTION 필요했음(기존 `draw_relic()`/`draw_relic_batch(integer)` 시그니처를 명시적으로 drop). 클라이언트는 `RelicGacha.jsx`가 `bonus_rubies` 합계를 계산해서 `onRubiesChange` 콜백으로 `App.jsx`의 `profile.rubies`를 즉시 갱신하고 토스트로 안내함
- 레벨 50: 82.5% / 레벨 100: 65% / 레벨 150: 47.5% / 레벨 199: 최저 30%(바닥)

**실패해도 레벨이 깎이지 않음** — 이 게임의 전반적인 "덜 가혹한" 톤(`ui-and-ux.md`의 디자인 완화 이력 참고)을 유지하기 위한 의도적 선택. 그냥 이번 중복 하나가 강화에 실패하고 사라질 뿐, 다음에 또 뽑으면 됨. 30% 바닥을 둬서 "사실상 불가능"해지는 구간이 없도록 함.

효과치 공식(서버 `calc_relic_bonus`/클라 `getRelicEffectiveValue`, 반드시 동일하게 유지):
```
rarity_mult(등급별) = 노멀 1.0 / 레어 2.0 / 에픽 3.6 / 전설 6.0 / 신화 10.0   -- (migration 145, 장비와 분리해서 유물 전용으로 재조정)
성장률(등급별) = 노멀 2% / 레어 3% / 에픽 4.5% / 전설 6.5% / 신화 9%   -- (migration 141, 신규, 사용자 요청)
효과치 = base_value × rarity_mult × (1 + level × 성장률[등급])
```
- ⚠️ **등급별 성장률 차등(migration 141, 사용자 요청 — "높은 등급일수록 강화 시 상승 갭을 더 크게")**: 기존엔 등급 상관없이 레벨당 +3%로 균일했음(`rarity_mult`만 등급별로 다르고 성장곡선은 동일) — 이제 성장률 자체도 등급이 높을수록 가팔라짐. `rarity_mult`(기본배율)와 성장률(레벨당 증가폭)이 둘 다 커지므로, 200강 만렙 기준 최상급-최하급 격차가 기존(6.5배 고정)보다 훨씬 커짐 — 신화(6.5×(1+200×0.09)=6.5×19=123.5배) vs 노멀(1×(1+200×0.02)=5배) ≈ **약 25배 격차**(기존엔 등급 곱 6.5배가 레벨과 무관하게 고정이었음)
- ⚠️ **기본배율/보유효과 추가 상향(migration 145, 사용자 재요청 — "비싼 돈을 쓰는 가치가 있게")**: `rarity_mult`를 장비와 공유하던 값(1/1.8/2.8/4.2/6.5)에서 유물 전용으로 분리해 더 가파르게(1/2.0/3.6/6.0/**10.0**) 재조정, 보유효과 비율도 10%→**20%**로 상향. **처음엔 rarity_mult를 신화 18배까지 잡고 성장률도 노멀2.5%~신화16%까지 같이 올리려 했는데, 배포 전 시뮬레이션으로 percent 타입 유물(예: 공격력% 유물)이 200강 기준 +475%까지 치솟는 걸 발견**(flat 타입은 절대치 합산이라 안전하지만, percent 타입은 `rarity_mult`와 성장률이 곱연산으로 계산되는 구조라 둘 다 올리면 위험하게 폭주함) — 성장률은 141 수준(노멀2%~신화9%)으로 되돌리고 `rarity_mult`와 보유효과 비율만 상향해서, 200강 만렙 mythic percent 유물 하나의 최대 효과가 기존 36.4%에서 **152%**(약 4.2배)로 강해지되 "유물 하나로 스탯이 5배 뛰는" 수준의 붕괴는 피함
- ⚠️ **UI 표시 누락 버그(사용자 재제보 — "보유효과 넣어달라고 했는데 안 들어갔다")**: 141에서 계산 로직(`calc_relic_bonus`)엔 보유효과를 이미 반영해뒀는데, `RelicGacha.jsx` 화면 어디에도 "보유효과"라는 텍스트/수치가 안 보였음 — 실제로는 작동하고 있었지만 사용자가 확인할 방법이 전혀 없어서 "안 들어간 것"처럼 보였던 표시 누락 버그. 각 유물 카드에 `formatRelicEffect(relic, level, true)`로 보유효과 수치를 별도 줄로 표시하고, 상단 안내 문구도 "보유만 해도 소량 효과"를 명시하도록 수정

## 밸런스 설계 (사용자 요청: "밸런스가 너무 튀지 않게")

**핵심 안전장치는 "최대 장착 제한"**(최초 3개, 131에서 5개로 확장 — 사용자 요청). 만약 보유한 유물 전부(최대 50개)가 장비처럼 "보유효과"로 항상 적용됐다면, 후반부에 유저가 유물을 많이 모을수록 파워가 무한정 누적되는 구조가 되어 기존 장비/스킬 시스템을 압도할 위험이 컸음. 대신 "장착한 것만" 전액 적용되게 해서 총 파워를 구조적으로 제한함 — 장비(4슬롯 고정 카테고리)와 달리 유물은 50종 중 자유 선택이라 "어떤 5개를 낄지"라는 전략적 재미는 남기면서도 파워 총량은 항상 최대 5개 몫(+미착용분의 10% 보유효과)으로 묶여있음.
- ⚠️ **141에서 보유효과가 추가되며 이 설계가 일부 완화됨**(사용자가 명시적으로 요청) — 50개를 전부 모으면 "장착 5개 전액 + 미장착 45개의 10%"가 누적되므로, 극단적으로 많이 모은 유저는 예전보다 확실히 더 강해짐. 다만 10%라는 비율 자체가 작아서(장착 1개의 가치가 미장착 10개어치와 맞먹는 수준), "그래도 장착이 압도적으로 유리하다"는 구도는 유지됨.

**참고**: 50종 유물은 카테고리(hp/atk/def/...)×방식(flat/percent) 조합당 등급별로 딱 1종씩만 존재(예: "신화 등급 공격력% 유물"은 전체 카탈로그에 단 1개)라, 5칸을 전부 채워도 같은 카테고리를 여러 개 겹쳐 낄 수는 없음 — 자연스럽게 "어떤 5개를 고를지" 서로 다른 카테고리를 섞는 선택이 됨. 극단적 계산(신화 등급 + 200강 ATK%/DEF%/HP%/쿨감%/골드% 5종을 전부 장착, 현실적으로 가능한 최대 조합): ATK/DEF/HP는 각각 0.8% × 6.5 × 7 ≈ 36.4%p씩(카테고리당 1개뿐이라 중첩 안 됨), 쿨감·골드도 마찬가지로 각각 최대 36.4%p 수준. 이 정도 도달하려면 5종 전부 신화 등급으로 뽑고 각각 200강까지(성공확률이 갈수록 낮아지는) 강화해야 하는 극단적 엔드게임 투자가 필요함. 일반적인 유저(에픽~전설 등급, 낮은~중간 강화)는 카테고리당 한 자릿수 % 수준의 보너스만 받게 되어 기존 시스템을 압도하지 않는 "보조 성장 수단"으로 설계됨.

## 적용 범위 (의도적으로 제한된 부분)

전투가 부분적으로 클라이언트에서 계산되는 이 게임 구조상(`security.md`의 "알려진 한계" 참고), 유물 효과의 적용 범위를 다음과 같이 명시적으로 제한함:

- **체력/공격력/방어력(flat+percent)**: 서버(PvP 전투력·랭킹) + 클라이언트(전투 화면) 양쪽 다 반영. `App.jsx`의 `equipmentBonus` 객체에 유물 몫을 합산해서 넘기므로, 전투/던전/전직던전/월드보스 4개 전투화면 **전부** 자동으로 적용됨(화면별로 따로 손댈 필요 없음 — 기존 장비 보너스와 같은 파이프라인을 타기 때문)
- **골드 획득%**: **자동사냥(`grant_idle_reward`)에만** 반영 — 105(주말보너스)/062(황금몬스터)와 동일한 범위 제한 원칙. 스테이지 클리어/던전/탑/월드보스 개별 보상 함수는 범위 밖(건드리지 않음)
- **경험치 획득%**: `BattleScreen.jsx`의 **자동사냥 경험치에만** 반영(골드와 동일한 범위 제한 논리) — 스테이지 도전(챌린지 모드) 클리어 경험치는 범위 밖
- **스킬 쿨타임 감소%/버프 효과%**: **`BattleScreen.jsx`(일반 전투 화면)에만** 반영 — 던전/전직던전/월드보스 전투화면은 이번 1차 범위에 포함 안 함(4개 화면 전부 손대기엔 회귀 리스크 대비 이득이 낮다고 판단, 필요하면 추후 확장). 쿨타임 감소는 최대 90%까지, 버프 강화로 인한 haste 감소도 최대 95%까지 안전 클램프(0 이하로 내려가 타이머가 깨지는 것 방지)

## 뽑기 UI (`RelicGacha.jsx`)

상점의 6번째 탭 "🏺 유물 뽑기" — 뽑기 중 **가격이 가장 비쌈**(130에서 인상, 사용자 요청): 레벨1 기준 **1,000골드**, 뽑기레벨당 **+300골드**씩 증가(스킬 300골드·장비 100골드 기준가보다 훨씬 비쌈). 1회/10회/**100회**(신규, 사용자 요청) 뽑기 버튼 제공. **일일 무료뽑기 대상에도 포함**(130 이전엔 의도적으로 제외했었는데, 사용자 요청으로 6번째 무료뽑기 슬롯으로 추가 — `daily_free_draw_state`의 `draw_type` 체크 제약에 `relic` 추가, `claim_daily_free_draw`가 반환컬럼 3개(`relic_key`/`enhance_attempted`/`enhance_success`) 추가돼 DROP FUNCTION 필요). 뽑기 결과 카드에 강화 성공/실패를 색으로 구분 표시(성공 초록 계열/실패 빨강 계열), 결과 공유 버튼도 동일 패턴으로 지원. 화면 하단에 보유 유물 목록(등급 내림차순 정렬)이 카드 그리드로 뜨고, 카드를 탭하면 장착 선택(최대 5개, 초과 시 토스트로 안내) → "장착 저장하기" 버튼으로 서버에 반영.

## 알려진 제약사항 / 후속 검토 항목

- PvP 상대의 유물 보너스도 서버에서 실시간 계산되므로(계산 비용 증가), 랭킹/매칭 조회가 살짝 느려질 수 있음(체감상 무시할 수준으로 판단, 문제되면 캐싱 검토)
- 던전/전직던전/월드보스 전투화면엔 쿨타임감소%/버프% 미반영(위 "적용 범위" 참고) — 사용자 반응 보고 확장 검토
- ✅ 유물 획득 관련 업적 추가됨(migration 124): **🏺 유물 수집가**(20종 보유, 6000골드), **💎 유물의 대가**(하나를 200강까지 강화, 30000골드). `achievementStats`의 `relicCount`/`maxRelicLevel`은 상점의 `RelicGacha.jsx`가 독립적으로 유물 목록을 관리해서, 업적 화면의 진행률이 로그인 시점 기준으로만 갱신됨(뽑은 직후 바로 반영 안 될 수 있음) — `totalSkillDraws` 등 기존에도 있던 것과 같은 성격의 사소한 지연, 치명적이지 않아 그대로 둠
- ⚠️ **성능 버그 수정(migration 133, 사용자 제보 — "100회뽑기가 다른 뽑기보다 오래 걸린다")**: 장비/스킬 뽑기는 `draw_equipment_batch`/`draw_skill_batch`처럼 N회를 **서버 반복문 안에서 한 번에 처리하고 결과를 한꺼번에 반환**하는 배치 RPC가 있는데, 유물은 그게 없어서 클라이언트(`drawRelicBatch`)가 `draw_relic()`을 100번 각각 순차 `await`로 호출했음 — 매 호출마다 왕복 네트워크 레이턴시가 그대로 누적되는 구조라 100회면 다른 뽑기보다 훨씬 느렸음. `draw_equipment_batch`와 동일한 "반복문+`return next`" 패턴으로 `draw_relic_batch(p_count)`를 신설해서 한 번의 요청으로 끝나게 함 — 강화 성공/실패 로직도 그대로 배치 안에 포함(반복마다 `enhance_attempted`/`enhance_success` 각각 판정). 클라이언트 `drawRelicBatch`는 이제 이 RPC를 한 번만 호출.
- ⚠️ **버그 수정(사용자 제보)**: `.relic-card`가 `<button>`인데 `color`를 별도로 지정 안 해서, 이름 텍스트(`.relic-card-name`)가 브라우저 기본 버튼 텍스트색(어두운 계열)으로 렌더링돼 다크 테마 배경에서 거의 안 보이던 문제. `color: var(--text-primary)`로 명시해서 수정.
