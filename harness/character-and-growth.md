### 능력치 상세 카드 (`MyPage.jsx`)

마이페이지에 "기본(레벨·전직) / 장비 보너스 / 스킬 보유효과 / 최종" 4행 표로 ATK/DEF/HP 구성을 투명하게 보여줌. 전투 화면들에 내려주던 `equipmentOnlyBonus`(용의 버프 배율 미적용 순수 장비 보너스)와 `skillPossessionAtk`를 그대로 재사용. 용의 버프가 켜져있으면 표 아래에 "전투 시 20배 적용"만 별도 안내하고, 표 자체는 배율 적용 전 값으로 유지해서 "순수 강함"과 "전투 중 실제 강함"을 구분함.

### 몬스터 애칭 (migration 058)

`owned_monsters.nickname`은 001부터 있었지만 어디서도 쓰인 적 없는 죽은 컬럼이었음(재검토 중 발견). 마이페이지 "대표 몬스터" 행 아래에 애칭 편집 UI를 추가해 연결함.

- `set_monster_nickname(p_nickname)` — 1~12자(한글/영문/숫자), `null`이면 애칭 해제
- `hydrateMonster()`가 `nickname || speciesName`으로 표시 이름 결정 — 애칭을 지으면 전투 로그, 헤더 등 `player.name`을 쓰는 모든 곳에 자동 반영(`speciesName`은 별도 필드로 항상 보존)
- 계정 닉네임(`profiles.nickname`, 평생 1회만 수정)과는 완전히 별개 — 애칭은 유일성 제약도 없고 자유롭게 여러 번 변경 가능
- **랜덤 이름 추천**(신규, `lib/nameSuggestion.js`) — 애칭 입력창 옆 "🎲 추천" 버튼으로 속성(불/물/풀)에 맞는 이름 후보를 무작위 채움. 순수 클라이언트 정적 목록(속성별 8개), 서버 호출 없음

### 인기 속성 통계 (migration 068, 신규 콘텐츠)

도감 하단에 "🌍 전체 유저 계약 속성 비율" 막대그래프. `owned_monsters`가 "본인만 조회" RLS라 전체 집계는 `fetch_element_popularity()`(security definer)가 개인정보 없이 속성별 인원수/비율(%)만 반환. 활성 몬스터가 없는 유저는 `is_active = true` 필터로 자동 제외.

### 몬스터 도감 (`MonsterDex.jsx`)

마이페이지 상단의 3×3(속성×진화단계) 그리드. 서버에 "발견 기록"을 저장하지 않고 **매번 클라이언트에서 활성 몬스터의 현재 속성/단계를 기준으로 계산**함 — 내 속성과 같고 도달한 단계 이하만 스프라이트가 보이고 나머지는 실루엣(`?`) 잠김. 스타터 1종만 계약해 진화시키는 구조라 다른 두 속성은 항상 미발견 상태가 정상(포획 기능 생기기 전까지). 발견된 칸에는 `speciesData.js`의 **레벨1 기준 기본 스탯**도 표시해 다음 진화가 얼마나 강한지 가늠할 수 있게 함(실제 성장치 아님을 안내문에 명시). 별도 보상 없는 순수 수집 열람 화면.

## 레벨업/스탯 성장

- **레벨업 경험치**: `expToNextLevel(level) = round(20 * level^1.5)`
- **스탯 성장**: `base스탯 × (1 + (level-1)*0.12) × 전직배율`
- `speciesKeyToDbId`/`dbIdToSpeciesKey`(`speciesDbIds.js`)로 클라이언트 키(`fire_1` 등)와 DB `species_id`(정수)를 매핑

## ⚠️ 던전 클리어 경험치 대폭 감소 (migration 168, 사용자 요청 — "만렙까지 너무 쉬움")

경험치던전(3.2→0.8)/골드던전(0.6→0.15)/전직던전·무한의탑(1.5→0.375)/루비던전(0.05→0.0125)/연승던전(0.06→0.015) 전부 배율을 약 1/4로 축소, 경험치던전 상한도 20만→5만으로 비례 축소. 전부 클라이언트 전용 값(서버 미러 없음)이라 이 migration 자체에는 SQL 변경이 없고, 아래 정예레벨 시스템(같은 migration)과 묶어서 "만렙까지 몇 개월씩 걸리게" 하는 하나의 밸런스 조정으로 취급함. 골드 보상은 손대지 않음(경험치만 조정 대상).

## 정예레벨(Elite Level) 시스템 (migration 168, 신규, 사용자 요청)

레벨 500(현재 만렙) 달성 후 시작되는 별도의 2차 성장축. "만렙 찍고 나면 얻는 경험치가 그냥 버려져서 할 게 없어짐"을 방지하기 위해, `applyExpGain`(`growth.js`)이 `level >= MAX_LEVEL`이 되면 남는 경험치를 버리는 대신 `eliteExp`에 그대로 이어서 누적시키고, 정예레벨 전용 커브로 레벨업시킴.

- **커브**: `eliteExpToNextLevel(eliteLevel) = round(2000 * eliteLevel^1.8)` — 일반 레벨 커브(`20*lv^1.5`)보다 훨씬 가파름
- **최대 100레벨**, 100레벨 전체 총 필요경험치는 약 2억 8,800만 — 일반 레벨 500 총량(약 4,460만)의 **약 6.5배**가 되도록 계수(2000)를 역산해서 설계함(정확한 소요 기간은 추정치, 다른 밸런스 수치와 동일하게 실제 반응 보고 재조정 가능)
- **DB**: `owned_monsters.elite_level`(0~100, CHECK 제약)/`elite_exp`(bigint) 컬럴 신설. `save_monster_growth`(127) 재정의(파라미터 2개 추가라 DROP FUNCTION 필요) — 정예레벨은 반드시 `level=500`일 때만 0보다 클 수 있고, 한 번에 급격히(20레벨 초과) 오르면 거부하는 등 기존 레벨 검증과 동일한 스타일의 방어 로직 추가. diff로 기존 검증 로직 100% 보존 확인
- ⚠️ **지금은 순수 카운터(스탯 보너스 없음)** — 정예레벨 자체가 전투력에 영향을 주지 않음. 이 레벨을 기준으로 한 **던전 입장 제한은 추후 별도 작업으로 예정**돼있음([`todo.md`](./todo.md) 참고)
- UI: `MyPage.jsx`(캐릭터 카드)와 `BattleScreen.jsx`(전투 중 HP바 라벨)에 `Lv.500 ✨정예 Lv.N` 형태로 표시. 나머지 8개 전투화면(던전/월드보스 등)에는 아직 표시 안 함(범위 밖, 후속 과제)

## 스킬 보유효과 PvP/전투력 반영 (migration 171, todo.md 후속과제 이행, 사용자 요청)

`sumSkillPossessionBonus`(클라이언트, `skillCatalog.js`)는 이미 계산하고 있었지만 서버 PvP/전투력 계산엔 반영된 적이 없었음. 예전엔 "50종 계산식을 통째로 SQL로 포팅해야 해서 범위가 큼"이라고 `todo.md`에 남겨뒀었는데, 실제로 확인해보니 보유효과 공식은 **등급**(`skill_catalog.rarity`, 이미 서버에 있음)과 **스킬레벨**(`user_skills.skill_level`, 역시 이미 서버에 있음)만 있으면 계산 가능해서(스킬별 50종 "사용 시 효과"와는 무관한 별개의 단순 공식) 예상보다 범위가 작았음.

- `calc_skill_possession_bonus(p_user_id)` 신설 — 클라이언트 공식과 동일하게 유지할 것
- `fetch_my_combat_power`/`fetch_leaderboard`/`fetch_public_profile`/`start_pvp_battle`/`start_pvp_revenge_battle` 5개 함수 재정의(전부 반환타입 그대로, DROP 불필요) — atk 항에 스킬 보유효과를 더함(장비/유물 보너스와 동일하게 relic 퍼센트 배율 적용 **전** 단계에 합산)
- ⚠️ **덤으로 발견한 버그**: `start_pvp_revenge_battle`(복수전)에 유물(relic) 보너스 자체가 아예 빠져있었음(메인 PvP는 반영하는데 복수전만 누락) — 정기점검이 아니라 이번 배치 작업 중 우연히 발견, 스킬 보유효과와 함께 같이 수정함
- 5개 함수 전부 diff로 순수 추가만 있는지 검증 완료

## 속성 상성 시스템 (migration 없음, 순수 클라이언트, 사용자 요청)

이전엔 "파급 범위가 매우 커서 사용자 승인 없이 진행하지 않음"으로 `todo.md`에 남겨뒀던 항목 — 이번에 사용자가 직접 요청해서 구현함. 스테이지 난이도 곡선을 크게 흔들지 않기 위해 **배율을 온건하게**(유리 1.25배 / 불리 0.8배) 잡아서, 기존 HP/ATK/DEF 공식은 전혀 손대지 않고도 "상성이 있다"는 전략적 재미만 얹는 방향으로 설계함.

- **상성 순환**: 불 > 풀 > 물 > 불(`lib/elements.js`의 `getElementMultiplier`) — 클래식 3속성 상성
- **몬스터 속성**: 스테이지/던전/무한의탑 몬스터는 이미 전부 `element` 필드가 있었음(챕터/층수 기반 순환 배정, 지금까지는 스프라이트 테마 용도로만 쓰였음) — 이번에 처음으로 전투 계산에 실제로 연결함. 루비/봉인/연승 던전 보스는 element가 없었어서 새로 고정 배정(각각 fire/water/fire, 테마에 맞춰 선택)
- **스킬 속성**: 50종 갸챠 스킬 전부(`skillCatalog.js`) + 폴백 스킬 5종(`skills.js`, 전부 불 속성 테마라 fire로 고정)에 `element` 필드 신규 부여. 일부(화염탄=fire, 물살가르기=water 등)는 이름 그대로 배정, 나머지는 균등 분포(인덱스 순환)로 배정
- **적용 지점**: `mitigateDamage(rawDamage, defenderDef, elementMultiplier)`에 3번째 인자로 하위호환 추가(생략 시 기존과 동일하게 1배) — 8개 전투화면(PvP연출 제외) 전부 22곳의 호출부에 `getElementMultiplier(스킬속성, 적속성)`(플레이어 공격) 또는 `getElementMultiplier(적속성, 플레이어속성)`(적 공격)을 연결
- heal/stun/buff/haste 타입 스킬에는 적용 안 함(상성이 의미 있는 건 실제 데미지를 주는 damage/dot 타입뿐)
- `npm run build` 통과 확인, 22개 호출부 전부 정상 연결 확인
- 후속 과제(범위 밖): 전투 화면에 "상성 유리/불리" 시각적 안내(로그 문구/아이콘 등)는 아직 없음 — 필요하면 `todo.md`에 추가 가능

## 정예의 시련 던전 (migration 172, 신규 콘텐츠, 사용자 요청)

정예레벨(위 문단) **1부터 입장 가능한** 던전 — 레벨 500(만렙) + 정예레벨 최소 1회 달성이 필요한 진짜 엔드게임 콘텐츠.

- **보상 설계 고민**: 새 재화(파편류)를 또 만들지 않고 **"정예 경험치"**로 결정 — 레벨 500 상태에서는 `applyExpGain`이 얻는 경험치를 이미 자동으로 정예경험치로 돌려주므로(위 문단), 이 던전은 그 흐름을 재사용하는 "정예레벨 전용 고효율 파밍터" 역할만 하면 되고 새로운 경제 리스크가 전혀 없음
- **난이도**: 정예레벨에 비례해서 계속 강해짐(`getEliteTrialBoss(eliteLevel)`, `lib/eliteTrial.js`) — `maxHp = round(3000 + eliteLevel^1.6*400)` 등
- **보상량**: 클리어 1회당 "현재 정예레벨업까지 필요한 경험치"의 약 15% — 하루 3회 제한과 맞물려 대략 **2~3일에 정예레벨 1씩** 오르는 속도로 설계함(정예레벨이 오를수록 자연히 더 오래 걸림, 100레벨 전부 완주하면 약 7개월 상당 — 다른 밸런스 수치들과 동일하게 추정치, 실제 반응 보고 조정 가능)
- **서버 설계**: 골드 지급이 없어서(경험치는 다른 던전들과 동일한 클라이언트 신뢰 모델) 세션/클레임 RPC 자체가 불필요함 — `enter_elite_trial()`이 "정예레벨 1 이상"과 "하루 3회 제한"만 서버에서 강제하고, 승리 후 경험치 저장은 기존 `persistMonsterGrowth`/`save_monster_growth`(168) 그대로 재사용
- `EliteTrialBattle.jsx`는 `RubyDungeonBattle.jsx` 기반(단발성 보스 전투 구조 재사용), 골드/루비 지급 로직은 전부 제거하고 경험치만 남김
- `DungeonSelect.jsx`의 `EliteTrialPanel`은 정예레벨 0인 유저에게 "🔒 정예레벨 1 이상부터 입장 가능" 안내만 보여주고 입장 버튼 자체를 숨김(잠금 화면)

### ⚠️ 난이도 대폭 상향 + 일일 스킬 제한 (사용자 요청, 전직스킬 3.2배 상향과 함께 적용)

**보스 스탯 재설계**: 방어력을 특히 가파르게 올려서(`def = round(400 + eliteLevel^1.6*55)`, HP도 `round(15000 + eliteLevel^1.75*1400)`로 상향) `mitigateDamage`의 `100/(100+def)` 수렴 공식상 "강화 안 된 스킬로는 데미지가 거의 안 박히는" 체감을 의도적으로 만듦 — 전직스킬을 강화(`jobSkillEnhance.js`)하지 않고는 클리어가 어렵도록 설계함. 정확한 수치는 추정치, 실제 반응 보고 재조정 가능.

**일일 스킬 제한(`lib/eliteTrial.js`, 신규)**: 정예레벨 구간별로 특정 스킬을 아예 못 쓰게 막아서 "강화 안 한 일반 스킬 도배"를 막고 전직스킬 활용을 유도함.
- **1~19단계**: 치유(`heal`)/지속피해(`dot`) 타입 항상 금지(고정)

### ⚠️ 전직스킬 배율 3.2배 상향 (사용자 요청, 정예의 시련 난이도 상향과 함께 적용)

**설계 근거**: 강화 시스템(`jobSkillEnhance.js`, 최대 50레벨, 레벨당 +2% = 만렙 시 +100%/×2배)과 일반 뽑기 스킬의 최대 레벨(`skill_level` 최대 1000, [`skills.md`](./skills.md))을 비교해보니, 신화 등급 스킬을 **레벨 1000까지 강화**했을 때 배율이 약 160(`base≈40 × (1+999×0.003)≈4`) — 반면 기존 전직스킬은 10차 만렙강화(×2)해도 겨우 50(`25.0×2`)이라, "전직스킬이 궁극기"라는 설계 의도와 맞지 않게 오히려 신화 스킬에 크게 못 미쳤음. 이번에 **전직스킬 30종(3속성×10차) 전부 배율을 3.2배 상향**(예: 10차 `25.0→80.0`, 1차 `3.6→11.5`)해서, **10차를 만렙강화하면(×2) 배율 160으로 신화 스킬을 레벨 1000까지 강화한 것과 맞먹도록** 재조정함. 상위 전직차수일수록 여전히 더 센 구조(기존 배율 곡선의 상대적 비율은 그대로 유지, 전체를 동일 배율로만 스케일)는 그대로 유지됨.
- 이 변경은 전직스킬이 이미 상당한 진입장벽(레벨업 + 전직 던전 클리어, 6~10차는 추가 게이팅까지)이 있는 스킬군이라 파급 범위를 한정적으로 봤지만, 그래도 **기존 스테이지/던전 난이도 전반을 쉽게 만들 수 있는 큰 변경**이라는 점은 유의할 것 — 실제 반응을 보고 필요하면 다른 콘텐츠 난이도도 같이 조정할 수 있음([`todo.md`](./todo.md)에 감시 항목으로 기록)
- 전직 성공 시 **외형도 전용 그래픽으로 변경**(아래 "외형 변경" 참고)
- **최대 레벨 500** 신설(`growth.js MAX_LEVEL`, 10차 전직 요구 레벨 480보다 여유 있게 설정) — 만렙 도달 후엔 경험치가 무의미하게 계속 쌓이지 않도록 0으로 고정

"단순히 레벨만 조건으로 있는 게 아니라" 갈수록 여러 시스템에 걸친 조건이 필요하도록 설계:

- ⚠️ **칭호 이름 충돌 발견/수정**: 새로 만든 `pvp_win_300`에 "투기장의 지배자" 칭호를 배정하려는데, 기존 `pvp_win_50`(PvP 50승) 업적이 이미 이 칭호를 쓰고 있었음 — 50승 정도로 "지배자"라는 이름은 300승 업적과 격이 안 맞아서, `pvp_win_50` 쪽 칭호를 "투기장의 강자"(업적 표시명 "투기장 강자"와 통일)로 바꾸고 "투기장의 지배자"는 새 고난도 업적에 배정함
- ⚠️ **151 재조정(사용자 요청 — "무한의 탑은 2배, 가이드미션은 3배 정도" + "9차부턴 8차 기준으로 조금 더")**: 8차 기준값(탑60/미션25)에 탑×2/미션×3을 적용해 탑120/미션75로 상향. 9차·10차는 기존처럼 매 차수마다 큰 폭으로 벌어지지 않고, 8차 대비 완만하게(탑+20/미션+15씩) 증가하도록 재설계. **8차 요구업적도 재검토**: PvP 300승(`pvp_win_300`)은 "8차 전직 무렵 자연스럽게 달성"하기엔 너무 긴 별도 그라인딩이 필요하다고 판단해서, 레벨/장비가 쌓이면 자연히 오르는 전투력 지표 `power_100k`("압도적인 힘", 전투력 10만)로 교체. `pvp_win_300` 자체는 독립 업적으로 그대로 유지(게이팅에서만 빠짐) — **9차·10차 요구업적이 없다는 오해가 있었는데 재확인 결과 `power_1m`/`stage_clear_1000`으로 이미 정상 설정돼있었음**

- **서버(`start_job_dungeon`, 127)가 최종 검증** — `tower_progress.highest_floor`, `mission_state.mission_number`, `achievement_claims`를 직접 조회해서 확인. 클라이언트(`JobDungeonPanel`)는 탑층수/미션진행은 미리 체크해서 버튼을 비활성화하지만, **업적 보유 여부는 클라이언트에서 미리 확인하지 않음**(서버 에러 메시지로만 안내) — 굳이 클라이언트에 업적 목록을 따로 긁어오는 배선을 추가하지 않고, 이미 확립된 "서버가 최종 진실"이라는 원칙에 기댐
- 판정식이 클라이언트(`JOB_DUNGEON_EXTRA_REQ`, 안내용)와 서버(`start_job_dungeon`, 실제 검증) 양쪽에 각각 있어 **하나를 바꾸면 반드시 둘 다 같이 바꿔야 함**(100/121의 "행운/요일 던전" 판정식 이중관리와 동일한 주의사항)

### 캐릭터 카드 요약 (신규 콘텐츠, `MyPage.jsx`)

마이페이지 상단에 닉네임+칭호, 대표 몬스터, 4개 핵심 지표(PvP 티어/무한의 탑 최고층/업적 개수/클리어 스테이지)를 보여주는 요약 카드. 흩어진 정보를 한 곳에 모아 진행 상황을 바로 파악 가능하게 함.

- 새 서버 호출은 업적 개수(`fetchClaimedAchievements`, 기존 함수 재사용) 하나뿐, 나머지는 이미 로드된 데이터
- 2열 그리드 레이아웃이라 넘침 위험이 낮음, 극단값(다이아몬드+9999층+29/29+1000/1000)으로 실측 검증 완료

### 성장 곡선 미리보기 (신규 콘텐츠, `MyPage.jsx`)

능력치 상세 카드 아래에 "현재 전직 단계 기준 레벨만 올랐을 때"의 예상 스탯(현재/+10/+30/+50레벨) 표. `growth.js`의 `scaleStats(species, level, unlockedJobTier)`를 그대로 재사용(이미 실전 검증된 공식) — 순수 클라이언트 계산, 서버 호출 없음.

- 장비/스킬 보너스는 의도적으로 미포함(순수 종족 성장곡선용)임을 안내문에 명시
- "현재 전직 단계 기준"이라는 전제를 명확히 표기해 미래 진화/전직에 대한 오해 방지
- 큰 숫자(백만 단위) 조합 모바일 넘침 없음 재검증
- **전투력 컬럼 추가**(사용자 경험 개선) — 각 레벨 시점의 예상 전투력(`calculateCombatPower`)도 함께 표시해 성장폭을 한눈에 비교 가능. 5개 컬럼 극단값 조합 모바일 넘침 없음 재검증 완료
- ⚠️ **버그 수정(사용자 제보 — "테이블 데이터가 안 뜬다")**: 표시할 레벨 목록(현재/+10/+30/+50)을 `lv <= 200`으로 하드코딩해서 걸러내고 있었는데, 전직 6~10차 확장(127)으로 최대레벨이 500까지 늘어난 뒤에도 이 상한을 안 고쳐서, **레벨 200 이상인 유저는 행이 전부 걸러져 표 전체가 텅 비어 보였음**. `growth.js`의 `MAX_LEVEL`(500)을 그대로 참조하도록 수정 — 새 레벨 상한이 바뀌어도 이 표가 다시 낡지 않도록 하드코딩 대신 상수 재사용으로 변경

### 다음 목표 위젯 (신규 콘텐츠, `lib/nextGoals.js`)

캐릭터 카드 하단에 "🎯 다음 목표" 칩 리스트 — PvP 다음 티어까지 남은 승수, 무한의 탑 다음 10층 마일스톤, 다음 출석 마일스톤(7/30/100/200), 코스튬 컬렉션 완성까지 남은 종수(20종 기준), 전투력 마일스톤(10K/100K/1M, 083 연동), 던전 깊이 마일스톤(100/300/500, 088 연동), 스킬 컬렉션(50종, 092 연동), 최고 강화수치(+1000, 091 연동) — 총 8개 목표를 순수 클라이언트 계산으로 통합(서버 호출 없음, 이미 로드된 데이터만 조합). `pvpTier.js`의 `getWinsToNextTier` 등 기존 헬퍼 재사용. 전투력은 `MyPage.jsx`의 스탯 상세 카드가 계산해두는 최종 atk/def/hp를 `calculateCombatPower`에 넣어 산출(서버 `fetch_my_combat_power()`와 정확히 같지 않을 수 있으나 순수 참고용 위젯이라 문제없음). 신규 유저가 아무 목표도 안 채웠을 때(8개 칩 동시표시) 최악의 경우까지 모바일 실측 검증 완료(넘침 없음).

### 연속 접속 스트릭 표시 (신규 콘텐츠, `lib/loginStreak.js`)

캐릭터 카드에 "🔥N일 연속 접속" 배지(2일 이상일 때만). **순수 클라이언트 동기부여용**이고 보상 계산엔 미사용 — `localStorage`로 "이 기기에서 어제도 접속했는지"만 비교해 이어가거나 리셋. 서버 검증 없는 값이라 기기 변경/데이터 삭제 시 리셋되지만, 보상과 무관한 재미 요소라 문제없음.

### 다음 레벨까지 예상 소요시간 (신규 콘텐츠, `lib/idleTimeEstimate.js`)

성장 곡선 카드에 "⏱️ 자동사냥만으로 다음 레벨까지 약 N분/시간" 추가 — 자동사냥 경험치 공식(`stages.js`의 `getIdleMonster`와 동일, 0.19 배율 반영)과 처치 텀(1.5초)을 재사용해 순수 클라이언트로 추정. 챕터는 클리어한 스테이지 수(`clearedCount / 10`)로 근사. "스테이지 도전/던전 등을 병행하면 더 빨라진다"는 문구로 "이게 최소 하한선"임을 안내. 레벨5~220 전 구간 2분~10분 수준의 합리적 범위임을 시뮬레이션 확인, 모바일 줄바꿈도 검증 완료.

⚠️ **이중 공식 동기화 필수**: `idleTimeEstimate.js`의 `idleExpPerKill`이 `stages.js`의 `getIdleMonster` 경험치 공식을 **재사용이 아니라 그대로 복사**해서 갖고 있음(주석에도 명시) — 자동사냥 경험치 절반 감소(신규, 사용자 요청) 반영할 때 `stages.js`만 고치고 이 파일을 안 고쳤다면 "예상 소요시간"이 실제보다 2배 빠르게(절반만) 표시되는 조용한 버그가 났을 것. 두 파일 다 `hp*0.19*0.5`로 동일하게 반영 완료 — **앞으로 자동사냥 경험치 공식을 또 바꿀 때는 이 두 파일을 반드시 같이 고칠 것**(100/121의 "행운/요일 던전" 이중관리, 127의 "게이팅 조건 이중관리"와 동일 성격의 주의사항).
