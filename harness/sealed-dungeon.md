# 봉인된 던전 (migration 159/160, 신규 콘텐츠, 사용자 요청)

관련 파일: `SealedDungeonBattle.jsx`, `lib/sealedDungeon.js`, `DungeonSelect.jsx`(`SealedDungeonPanel`), migration 159/160

## 설계 배경 — 사용자의 명시적 방향 전환

지금까지 세션에서 추가한 던전들(연승 던전, 골든타임, 길드 레이드)은 전부 **골드를 더 많이 주는** 방향이었음. 사용자가 "유저가 너무 쉽게 만렙되고 재화가 넘쳐나게 하지 말고, 오히려 게임에 오래 머무르게 하는 방향"을 명시적으로 요청 — 그래서 이 던전은 정반대로 설계함.

## 핵심 설계 원칙 3가지

1. **골드/경험치를 단 1도 주지 않음** — `SealedDungeonBattle.jsx`는 승리해도 `applyExpGain`을 아예 호출하지 않음(다른 단발성 던전인 루비 던전은 승리 시 소량의 경험치를 항상 줬던 것과 정반대). 레벨업 속도나 골드 총량에 전혀 영향을 주지 않는, 완전히 분리된 보상 트랙("봉인의 파편")만 지급
2. **입장권이 하루 1개만 자연 생성, 최대 3개까지만 저장** — `profiles.seal_keys`/`seal_keys_claimed_date` 컬럼으로 관리. 골드로 구매 불가, 다른 재화로 전환도 불가. 하루 만에 몰아서 파밍할 수 없고, 여러 날에 걸쳐 "오늘의 몫"만큼만 진행되도록 강제해 자연스러운 재방문 주기를 만듦. 열쇠를 안 쓰고 쌓아둬도 3개에서 캡되므로("최대 3개") 장기간 접속 안 하다 몰아서 파밍하는 것도 막힘
3. **보스는 루비 던전보다 약 1.4배 강함**(레벨 1~500 전 구간 시뮬레이션으로 비율 확인) — 장비/스킬 세팅이 충분해야 깰 수 있는 "실력 체크" 성격. 보상이 순수 수집/랭킹용이라, 난이도를 낮춰 접근성을 높이기보다 "도전 자체의 성취감"에 무게를 둠

## 공식

```
calc_sealed_dungeon_boss(level):        # 클라이언트 getSealedDungeonBoss와 동일 공식 유지할 것
  hp  = round(2000 + level^1.5*56)      # 루비던전(1500+level^1.5*40) 대비 약 1.4배
  atk = round(110  + level^1.3*8.4)
  def = round(85   + level^1.2*5.6)

파편 보상 = 고정 3개/클리어 (레벨/장비/난이도와 무관 - RNG도 없음, 순수 "도전 횟수 = 보상" 구조)
```

## 서버 설계

- `profiles.seal_fragments`(bigint, 영구 누적, 소비 불가) / `profiles.seal_keys`(integer, 0~3) / `profiles.seal_keys_claimed_date`(date) 3개 컬럼 추가
- `fetch_my_seal_status()` — 조회할 때마다 "오늘 아직 자연증가분을 못 받았으면" 자동 지급(3개 캡). 별도의 "출석 체크" 버튼 없이, 던전 탭을 열 때마다 자연스럽게 오늘 몫이 채워지는 방식(sync_world_boss의 지연생성 패턴과 동일 철학)
- `enter_sealed_dungeon()` — 열쇠 1개 소모(0개면 거부), `sealed_dungeon_sessions` 세션 발급(루비 던전과 동일한 "세션 생성 후 최소 1초" 안티치트 패턴)
- `claim_sealed_dungeon_reward(p_session_id)` — 세션 검증 후 파편 고정 3개만 지급. **골드/경험치 관련 코드가 이 함수 안에 아예 존재하지 않음**(add_gold 호출 없음) — 다른 던전들과 달리 "재화 클램프"를 신경 쓸 필요가 없는 유일한 던전
- `fetch_seal_leaderboard()`/`fetch_my_seal_rank()` — `profiles.seal_fragments` 기준 영구 누적 랭킹(무한의 탑/연승 던전과 동일 TOP20 패턴). "오늘 얼마나 벌었나"가 아니라 "지금까지 얼마나 꾸준히 도전했나"를 보여주는 지표라는 게 다른 랭킹들과의 차이

### 배포 전 검증

새 함수 5개 전체를 대상으로 "RETURNS TABLE의 OUT 파라미터명과 테이블 컬럼명이 겹치는데 별칭 없이 bare 참조하는 곳이 있는지" 정적 스캔(158에서 만든 것과 동일한 스캔 스크립트 재사용) — 전부 안전함을 확인(OUT 파라미터 대입, 별칭 처리, 또는 UPDATE SET 타깃처럼 원래 모호하지 않은 문맥뿐).

## 클라이언트 설계

- `SealedDungeonBattle.jsx`는 `RubyDungeonBattle.jsx`를 베이스로 하되 `applyExpGain` 호출을 통째로 제거 — 승리해도 `player` state의 레벨/경험치는 입장 시점 그대로 유지됨(전투 중 HP 변화만 반영)
- 승리 시 다른 던전들처럼 "확인" 버튼을 누른 뒤 별도 화면 전환 없이, 결과 화면에서 곧바로 서버에 보상을 요청하고 그 자리에서 "🗝️ 파편 +3 (누적 N)"을 보여줌 — 골드처럼 상단 헤더 잔액에 반영할 필요가 없어(파편은 소비 불가라 UI 어디에도 "잔액 표시" 개념이 약함) 결과 화면에서 바로 보여주는 편이 자연스럽다고 판단
- `DungeonSelect.jsx`의 `SealedDungeonPanel`은 보유 열쇠(0~3)와 누적 파편, 리더보드를 보여줌. 열쇠가 0개면 버튼이 비활성화되고 "내일 자정 이후 자연 +1"이라는 안내가 항상 노출돼 있어, 골드로 살 수 없다는 걸 사용자가 헷갈리지 않게 함

## 업적 (migration 160)

연승 던전 업적(156)과 동일 패턴으로 `seal_fragments_100`(3,000골드)/`seal_fragments_500`(15,000골드)/`seal_fragments_2000`(60,000골드) 3종 추가. **업적 보상 자체는 골드로 지급**하지만(다른 업적들과의 일관성을 위해), **파편을 더 주지는 않음** — 파편 재화와 업적 보상 재화를 의도적으로 분리해서, "업적을 깰수록 파편이 잘 모인다"는 인플레 경로가 생기지 않게 함.

## 봉인의 상점 (migration 162/163, 신규 콘텐츠 — 파편 소비처)

파편이 랭킹/업적 말고는 쓸 곳이 없다는 걸 스스로 남겨뒀던 아래 "알려진 제한" 항목을 해소하기 위해 추가함 — 파편 전용 코스튬 4종(슬롯당 1개, "봉인" 테마, 각 150파편)을 신설.

- **기존 PvP 코스튬(20종)과 완전히 분리된 별도 테이블(`seal_costume_inventory`)** — 같은 풀에 섞으면 "PvP 코스튬 20종 전부 수집" 업적의 모수(20)가 조용히 24종 등으로 깨져버리기 때문. `pvp_costume_inventory`처럼 `item_catalog`에 대한 FK도 걸지 않음(장비 뽑기 확률표/희귀도 체계를 건드릴 위험을 원천적으로 피함)
- 클라이언트도 마찬가지로 `sealCostumeCatalog.js`라는 완전히 별도 상수 배열로 관리 — `itemCatalog.js`의 `ITEM_CATALOG`(장비 뽑기용 4슬롯×5등급 크로스곱)는 전혀 건드리지 않음. 대신 `getItem()`이 `ITEM_CATALOG`에서 못 찾으면 이 별도 배열도 확인하도록 폴백만 추가(뽑기 확률 로직은 `ITEM_CATALOG`를 직접 참조하지 않는 다른 함수라 영향 없음)
- 착용/해제는 기존 `set_costume_loadout`(042)을 재정의해서 재사용 — 보유 검증만 `pvp_costume_inventory` **또는** `seal_costume_inventory`에 있는지(UNION) 확인하도록 확장. 슬롯당 1개 제한 로직(`split_part(item_key, '_', 1)`)은 그대로 재사용됨(봉인 코스튬도 `weapon_seal`처럼 동일한 명명 규칙을 따르므로 수정 없이 호환)
- `MonsterSprite.jsx`의 코스튬 배지 색상 산출을 `RARITIES[item.rarity]` 대신 `item.color`를 우선 사용하도록 살짝 수정 — 기존 20종도 이미 `color` 필드를 갖고 있어 동작은 완전히 동일하고, `rarity` 개념이 없는 봉인 코스튬도 자연스럽게 지정한 색(보라색 `#8a4fff`)으로 표시됨
- 마일스톤 업적 `seal_costume_set`(4종 전부 보유, 8,000골드) 추가 — 착용 여부와 무관하게 "구매" 자체가 파편 600개를 쓴 의미 있는 이정표라고 판단해 장착까지는 요구하지 않음

### ⚠️ 세트효과 신설 - "순수 코스튬" 원칙의 의도적 예외 (사용자 요청)

4종을 **전부 장착**하면 실전투 데미지가 **250% 증폭(총 3.5배)**됨. 처음 설계할 때 "봉인 코스튬은 전투 스탯 영향 없음"을 명시적 원칙으로 못박았었는데, 이번 요청으로 그 원칙에 의도적인 예외를 둠 — 다만 진입장벽 자체가 무거움(파편 600개 구매 + 4슬롯 전부를 코스튬으로 채워야 해서 실제 코스튬 애정템을 포기해야 함)을 감안해 신중하게 설계함.

- `lib/sealCostumeCatalog.js`의 `hasFullSealCostumeSet(equippedCostumeKeys)`(4종 키가 전부 포함돼있는지 확인) + `SEAL_SET_DAMAGE_MULTIPLIER = 3.5` 상수 신설
- 적용 지점은 속성상성 배율(`getElementMultiplier`)과 동일한 자리 — `mitigateDamage(rawDamage, def, 상성배율 * 세트배율)`로 곱연산 결합. **9개 전투화면(PvP연출 제외) 전부**에 연결(전투화면 공통 로직이라 어디서든 4종 다 껴입으면 적용됨)
- **서버 PvP/랭킹 전투력 계산엔 반영 안 함**(용의 버프와 동일한 선례, [`world-boss.md`](./world-boss.md) 참고) — 실전투 데미지만 3.5배지 "전투력 수치" 자체를 부풀리진 않음. PvP 상대 매칭이나 랭킹 순위는 이 세트효과와 무관하게 그대로 계산됨
- `organisms/SealedDungeonPanel.jsx`의 상점 안내 문구를 "전투 스탯 영향 없음" → "4종 전부 장착 시 세트효과 250% 증폭" 안내로 교체, 실시간으로 세트효과 적용 중인지 배너로 표시

## 알려진 제한

- 열쇠를 3개까지 모아뒀다가 한 번에 3연속 도전하는 것 자체는 막지 않음(하루 파밍 총량 자체를 하드캡하는 건 아니고, "무한정 쌓아서 몰아치기"만 막는 설계) — 의도된 절충점: 열쇠 저장을 아예 막으면(예: 캡 1개) 하루라도 접속을 놓치면 그날 몫이 통째로 소멸해 오히려 스트레스를 줄 수 있어, 3개 정도의 여유를 의도적으로 둠
